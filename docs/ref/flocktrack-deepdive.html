App Overview

FlockTrack is a Progressive Web App that tracks church attendance for 500+ members. It works offline, costs zero dollars to run, and supports QR scanning, photo-grid quick tap, and search-based check-in. The entire backend is Google Sheets + Google Apps Script, hosted free on GitHub Pages.

Offline-First

Check-ins save locally first, sync to cloud later. Works without internet.

500+ Members

Handles a real congregation with photos, QR codes, and attendance history.

📷 QR Scan

Member shows their QR code. Camera reads it, extracts member ID, marks attendance instantly.

Q: "Tell me about a project you built."

I built FlockTrack, a Progressive Web App for my church that tracks attendance for over 500 members. It runs at zero cost using GitHub Pages for hosting, Google Sheets as the database, and Google Apps Script as the API layer. It works fully offline; check-ins save to the device's IndexedDB first and sync to the server in the background. It supports three check-in methods: QR code scanning via camera, a photo grid for quick taps, and name search. The entire frontend is a single vanilla JavaScript file with no build step, making it fast to load and easy to maintain.

    Architecture

    Data flow: User taps "Check In" on their phone. The app saves to IndexedDB instantly (offline-safe). In the background, it sends an HTTPS GET request to Google Apps Script with JSON-encoded data. Apps Script parses the request, writes to the appropriate Google Sheet tab, and returns a success response. If the network call fails, the entry stays in IndexedDB's sync queue and retries later.

    Think of it like a post office: IndexedDB is your outbox on your desk. You drop letters there instantly. The Service Worker is the mail carrier who periodically picks them up and delivers them to the post office (Google Apps Script). The post office files them in the correct drawer (Google Sheets tab). If the mail carrier can't make it today (no internet), your letters stay in the outbox and get delivered tomorrow.

    PWA Deep-Dive

    What IS a PWA?

    A Progressive Web App is a regular website that meets specific criteria to behave like a native app. When those criteria are met, the browser offers "Add to Home Screen." After installation, it launches without the browser address bar, has its own app icon, and works offline.

    A PWA needs three things: (1) HTTPS, (2) a Web App Manifest (manifest.json), and (3) a Service Worker. GitHub Pages gives you HTTPS for free. The manifest tells the phone how to display the app. The Service Worker intercepts network requests and enables offline mode.

    manifest.json

    This JSON file tells the browser: "This website is an app. Here's how to install it."

  "description": "Church attendance tracking PWA",
  "start_url": "/FlockTrack/",
  "display": "standalone",
  "background_color": "#121212",
  "theme_color": "#2196F3",
  "icons": [
    { "src": "icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "icons/icon-512.png", "sizes": "512x512", "type": "image/png" }

}

    display: "standalone"

    Hides the browser URL bar. App looks native. Other options: fullscreen, minimal-ui, browser.

    start_url

    Where the app opens when launched from home screen. Your entry point.

    theme_color

    Colors the phone's status bar and task switcher to match your app brand.

    icons

    The app icon on the home screen. Need multiple sizes for different devices.

    Service Worker (sw.js)

    A Service Worker is a JavaScript file that the browser runs in a separate thread. It sits between your app and the network, intercepting every HTTP request. Think of it as a programmable proxy.

    Service Worker = Bouncer at a club. Every request that leaves your app has to pass through the bouncer. The bouncer checks: "Do I have this in my cache (VIP list)?" If yes, serve it immediately without bothering the server. If no, let the request through to the network. If the network is down, serve a cached fallback or tell the user they're offline.

    FlockTrack's actual sw.js:

    JavaScript 
    const CACHE_NAME = 'flocktrack-v2';
const ASSETS = [
  '/FlockTrack/',
  '/FlockTrack/index.html',
  '/FlockTrack/icons/logo.png',
  '/FlockTrack/icons/icon-192.png',
  '/FlockTrack/icons/icon-512.png',
  'https://unpkg.com/html5-qrcode@2.3.8/html5-qrcode.min.js',
  'https://cdn.jsdelivr.net/npm/qrcodejs@1.0.0/qrcode.min.js'
];

// Install: cache all critical assets
self.addEventListener('install', event => {
  event.waitUntil(
    caches.open(CACHE_NAME)
      .then(cache => cache.addAll(ASSETS))
      .then(() => self.skipWaiting())
  );
});

// Activate: delete old caches
self.addEventListener('activate', event => {
  event.waitUntil(
    caches.keys().then(keys =>
      Promise.all(keys.filter(k => k !== CACHE_NAME).map(k => caches.delete(k)))
    ).then(() => self.clients.claim())
  );
});

// Fetch: cache-first for assets, network-only for API
self.addEventListener('fetch', event => {
  if (event.request.url.includes('script.google.com')) {
    return; // API calls go straight to network, never cached
  }
  event.respondWith(
    caches.match(event.request)
      .then(cached => cached || fetch(event.request))
  );
});

    Q: "Explain the Service Worker lifecycle."

    A Service Worker goes through three phases: Install, Activate, and Fetch. During Install, it downloads and caches all critical assets. During Activate, it cleans up old caches from previous versions. After activation, it intercepts all network requests in the Fetch event. In FlockTrack, I use a cache-first strategy for static assets (serve from cache, fall back to network) and network-only for API calls to Google Apps Script (because attendance data must always be fresh).

    Cache Strategy

    Cache-First (Assets)

    Check cache. If found, serve it. If not, fetch from network and cache the response. Used for HTML, icons, JS libraries.

    Network-Only (API)

    Always go to network. Never cache API responses. Attendance data must be fresh. If network fails, IndexedDB handles it.

    Offline-First Architecture

    IndexedDB

    IndexedDB is a browser-native database. Unlike localStorage (which only stores strings up to 5MB), IndexedDB stores structured objects, supports indexes for fast queries, and can hold hundreds of megabytes. It's asynchronous, so it never blocks the UI.

    IndexedDB = Your personal notebook. When you check someone in, you write it in your notebook immediately (instant). Later, when you have WiFi, you transcribe your notebook entries to the shared whiteboard (Google Sheets). Your notebook never runs out of pages and organizes entries by date automatically.

    How FlockTrack uses IndexedDB:

    JavaScript 
    // Open/create the database
const dbRequest = indexedDB.open('FlockTrackDB', 1);

dbRequest.onupgradeneeded = (event) => {
  const db = event.target.result;
  // Store for today's attendance (local cache)
  db.createObjectStore('attendance', { keyPath: 'memberId' });
  // Store for pending sync items (outbox)
  db.createObjectStore('syncQueue', { keyPath: 'id', autoIncrement: true });
  // Store for member data (offline access)
  db.createObjectStore('members', { keyPath: 'id' });
};

// Check-in: save locally FIRST, then sync
async function checkIn(memberId) {
  const record = { memberId, timestamp: Date.now(), synced: false };

  // 1. Save to IndexedDB immediately (user sees success)
  await saveToIndexedDB('attendance', record);
  showSuccessUI(memberId);

  // 2. Try to sync to server in background
  try {
    await syncToServer(record);
    record.synced = true;
    await saveToIndexedDB('attendance', record);
  } catch (e) {
    // Network failed. Record stays in syncQueue.
    await addToSyncQueue(record);
  }
}

    The offline-first pattern: (1) Write to IndexedDB. (2) Update UI immediately. (3) Try network in background. (4) If network fails, queue for retry. (5) On next sync cycle, flush the queue. The user NEVER waits for network. The server is authoritative; each sync cycle refreshes local data from the server's truth.

    Sync Queue & Retry Logic

    JavaScript 
    // Periodic sync: runs every 30 seconds when online
async function syncCycle() {
  if (!navigator.onLine) return;

  // 1. Flush outgoing queue
  const pending = await getAllFromStore('syncQueue');
  for (const item of pending) {
    try {
      await syncToServer(item);
      await deleteFromStore('syncQueue', item.id);
    } catch (e) {
      break; // Stop on first failure, retry next cycle
    }
  }

  // 2. Pull fresh data from server (server is authoritative)
  const serverData = await fetchTodayAttendance();
  await clearStore('attendance');
  for (const record of serverData) {
    await saveToIndexedDB('attendance', record);
  }
  updateUI();
}

    "Offline-first means the local data is the source of truth." No. In FlockTrack, the SERVER (Google Sheets) is authoritative. Local IndexedDB is a cache and an outbox. Each sync cycle clears local attendance and replaces it with server data. This prevents conflicts; if two devices check in the same person, the server deduplicates.

    Q: "How do you handle conflicts in offline-first?"

    FlockTrack uses a "last-write-wins with server authority" model. Local writes are fire-and-forget; they queue up and push to the server. The server deduplicates by member ID + date. On each sync cycle, local attendance is fully replaced by server data. This means if two devices check in the same person, both pushes arrive at the server, the server only keeps one record (deduplicated), and both devices converge on the same state at next sync. No complex CRDT or vector clocks needed for this use case.

    Backend: Google Apps Script

    What is Google Apps Script?

    Google Apps Script (GAS) is a serverless JavaScript runtime hosted by Google. It can access Google Sheets, Gmail, Drive, and Calendar natively. You write JavaScript, deploy it as a "Web App," and get a URL. That URL is your API endpoint. No server to manage, no hosting costs, no infrastructure.

    Google Apps Script = A secretary who lives inside Google's office. You send them a letter (HTTP request) with instructions. They read it, pull the right file from the cabinet (Sheets), update it, and send you a confirmation. They never sleep, never take vacation, and work for free (up to quotas).

    The doGet Handler

    Every request hits one function: doGet(e). The parameter e contains query string parameters. FlockTrack encodes the entire action + payload as JSON in a single data parameter.

    JavaScript 
    function doGet(e) {
  try {
    const payload = JSON.parse(e.parameter.data);
    const action = payload.action;

    switch (action) {
      case 'checkIn':
        return handleCheckIn(payload);
      case 'getMembers':
        return handleGetMembers(payload);
      case 'addMember':
        return handleAddMember(payload);
      case 'updateMember':
        return handleUpdateMember(payload);
      case 'addVisitor':
        return handleAddVisitor(payload);
      case 'bulkSync':
        return handleBulkSync(payload);
      case 'resendQR':
        return handleResendQR(payload);
      case 'sendReport':
        return handleSendReport(payload);
      case 'getConfig':
        return handleGetConfig();
      case 'registerDevice':
        return handleRegisterDevice(payload);
      default:
        return jsonResponse({ error: 'Unknown action' });
    }
  } catch (err) {
    return jsonResponse({ error: err.message });
  }
}

function jsonResponse(data) {
  return ContentService.createTextOutput(JSON.stringify(data))
    .setMimeType(ContentService.MimeType.JSON);
}

    Why GET Instead of POST?

    "GET is only for reading data." In REST theory, yes. In practice, FlockTrack uses GET for writes because of a real iOS Safari bug: when Apps Script redirects (302) after receiving a POST, iOS Safari drops the request body. The data never arrives. Converting all writes to GET (with JSON in the query string) bypasses this entirely. It's pragmatic engineering over theoretical purity.

    JavaScript 
    // Frontend: how a check-in request is sent
async function syncToServer(record) {
  const payload = {
    action: 'checkIn',
    memberId: record.memberId,
    timestamp: record.timestamp,
    deviceId: getDeviceFingerprint()
  };

  const url = SCRIPT_URL + '?data=' + encodeURIComponent(JSON.stringify(payload));
  const response = await fetch(url);
  const result = await response.json();

  if (result.error) throw new Error(result.error);
  return result;
}
// The entire payload rides in the URL query string as encoded JSON

    Q: "Why did you use GET for write operations? Isn't that wrong?"

    Technically, REST conventions say GET should be idempotent and read-only. However, I hit a real bug: iOS Safari drops POST bodies when Google Apps Script issues its required 302 redirect after deployment. The workaround is encoding the write payload as JSON in the GET query string. This is a pragmatic decision; the API is not public-facing, and the trade-off between theoretical REST purity and actually working on all devices was clear. Many internal APIs make similar compromises.

    JavaScript 
    // Column index mapping (avoids magic numbers)
const COL_MEM = { ID: 1, NAME: 2, EMAIL: 3, PHONE: 4, PHOTO: 5, QR: 6, GROUP: 7, STATUS: 8 };
const COL_ATT = { MEMBER_ID: 1, DATE: 2, TIME: 3, DEVICE: 4, METHOD: 5 };

function handleCheckIn(payload) {
  const sheet = SpreadsheetApp.getActiveSpreadsheet().getSheetByName('Attendance');
  const today = Utilities.formatDate(new Date(), 'Asia/Manila', 'yyyy-MM-dd');
  const time = Utilities.formatDate(new Date(), 'Asia/Manila', 'HH:mm:ss');

  // Check for duplicate (same member, same day)
  const data = sheet.getDataRange().getValues();
  const alreadyCheckedIn = data.some(row =>
    row[COL_ATT.MEMBER_ID - 1] === payload.memberId &&
    row[COL_ATT.DATE - 1] === today
  );

  if (alreadyCheckedIn) {
    return jsonResponse({ status: 'already_checked_in' });
  }

  sheet.appendRow([payload.memberId, today, time, payload.deviceId, payload.method]);
  return jsonResponse({ status: 'success' });
}

    Limitations & Why It Works Anyway

    Known Limitations of Google Sheets as DB

    ▼
    • Speed: Gets slow past 10,000 rows. Each read loads the entire sheet into memory.
    • No real queries: No SQL, no indexes. You filter arrays in JavaScript.
    • Concurrency: No row-level locking. Two simultaneous writes to the same row can conflict.
    • Quotas: Google limits Apps Script to 90 minutes execution/day, 20,000 email sends/day.
    • No relations: Can't JOIN tabs. Cross-tab lookups are manual.

    Why it still works for FlockTrack: Attendance is append-only (500 new rows/week max). Reads are bulk fetches (load all today's attendance). We'll never hit 10k rows in the attendance tab if we archive monthly. Concurrency isn't an issue because check-ins are sequential (one person at a time). The free tier quotas are way beyond what a 500-member church needs.

    Google Sheets = A shared whiteboard. Everyone can see it, anyone (with permission) can write on it, but you can't sort it faster than reading every sticky note. It works great when the whiteboard is small (hundreds of rows) and people take turns writing. It breaks when thousands of people write simultaneously or the board fills a whole wall.

    Device Access Control

    Not every phone should be able to mark attendance. FlockTrack requires device approval before check-ins work.

    JavaScript 
    // Generate a unique device fingerprint on first visit
function getDeviceFingerprint() {
  let fp = localStorage.getItem('deviceFingerprint');
  if (!fp) {
    fp = crypto.randomUUID(); // Browser-native UUID generator
    localStorage.setItem('deviceFingerprint', fp);
  }
  return fp;
}

// On app load: check if this device is approved
async function checkDeviceApproval() {
  const fp = getDeviceFingerprint();
  const result = await apiCall({ action: 'checkDevice', deviceId: fp });

  if (result.status === 'approved') {
    showMainApp();
  } else if (result.status === 'pending') {
    showPendingScreen(); // "Waiting for admin approval"
  } else {
    showRegistrationScreen(); // "Register this device"
  }
}

    Q: "How do you handle security in this app?"

    Security is layered. First, each device generates a unique fingerprint stored in localStorage. New devices must be admin-approved before they can check anyone in. Second, the Apps Script web app is deployed with "Anyone" access but validates the device fingerprint on every request. Third, the Google Sheet itself has restricted sharing. It's not bank-level security, but for a church attendance app, the threat model is "prevent unauthorized casual marking" not "defend against nation-state actors."

    Real-World Challenges Solved

    This section is GOLD for interviews. It shows you've shipped a real product used by real people and solved real problems. Interviewers love hearing about bugs you debugged and trade-offs you navigated.

    iOS Safari POST Body Bug

    ▼

    Problem: Google Apps Script, when deployed as a web app, responds with a 302 redirect on POST requests. Most browsers follow the redirect and include the body. iOS Safari drops the POST body on redirect, so the server receives an empty request.

    Discovery: Check-ins worked on Android and desktop but silently failed on iPhones. No error, just no data arriving at the server.

    Solution: Converted ALL write operations from POST to GET, encoding the payload as JSON in the query string: ?data=encodeURIComponent(JSON.stringify(payload))

    Trade-off: URLs get long. URL length limit is ~2048 chars in some browsers. Our payloads are small enough (member ID + timestamp), so this isn't a practical concern.

    Camera Not Releasing on iOS Tab Switch

    ▼

    Problem: On iOS, switching tabs or going to home screen while the camera is active causes the camera to stay "locked." When the user returns, the camera shows a black screen or the device overheats.

    Solution: Explicitly stop all media tracks when the QR scanner view is deactivated:

    JavaScript 
    document.addEventListener('visibilitychange', () => {
  if (document.hidden && isScannerActive) {
    qrScanner.stop();
    const video = document.querySelector('#qr-reader video');
    if (video?.srcObject) {
      video.srcObject.getTracks().forEach(track => track.stop());
    }
  }
});

    Flip Camera Black Screen

    ▼

    Problem: When user taps "flip camera" (front to rear or vice versa), the video element shows black.

    Root cause: The html5-qrcode library needs to fully stop before restarting with a different camera. Starting a new stream without stopping the old one causes a resource conflict.

    Solution: await qrScanner.stop() THEN start with new facingMode. The await is critical; without it, the stop hasn't completed before the new start fires.

    Deleted Check-ins Reappearing (Ghost Syncs)

    ▼

    Problem: Admin deletes a check-in from the server (mistaken check-in). But the device still has it in IndexedDB. Next sync cycle pushes it back to the server. The deletion "undoes" itself.

    Solution: 60-second local blacklist. When a deletion comes from the server (sync shows a record disappeared), the member ID goes into a blacklist with a 60s TTL. During those 60 seconds, the sync queue won't re-push that member's check-in. After 60s, the local IndexedDB has been refreshed from server (which no longer has the record), so it stays deleted.

    JavaScript 
    const deleteBlacklist = new Map(); // memberId -> expiry timestamp

function blacklistMember(memberId) {
  deleteBlacklist.set(memberId, Date.now() + 60000);
}

function isBlacklisted(memberId) {
  const expiry = deleteBlacklist.get(memberId);
  if (!expiry) return false;
  if (Date.now() > expiry) { deleteBlacklist.delete(memberId); return false; }
  return true;
}

    Duplicate Registrations (Name Matching)

    ▼

    Problem: "Maria Santos" registers. Later "Maria C. Santos" registers again. Or "maria santos" (lowercase). Now you have duplicate members.

    Solution: A namesMatch() function that normalizes and fuzzy-matches:

    JavaScript 
    function namesMatch(name1, name2) {
  const normalize = (n) => n.toLowerCase().trim()
    .replace(/[^a-z\s]/g, '') // Remove punctuation
    .replace(/\s+/g, ' ');     // Collapse spaces

  const n1 = normalize(name1);
  const n2 = normalize(name2);

  if (n1 === n2) return true;

  // Check if one is a subset of the other (handles middle initials)
  const parts1 = n1.split(' ');
  const parts2 = n2.split(' ');
  const shorter = parts1.length < parts2.length ? parts1 : parts2;
  const longer = parts1.length >= parts2.length ? parts1 : parts2;

  return shorter.every(part => longer.some(p => p.startsWith(part) || part.startsWith(p)));
}

    Splash Screen Timing

    ▼

    Problem: On fast connections, the splash screen flickers (appears for 50ms then disappears). Looks janky. On slow connections, user stares at a blank screen.

    Solution: Enforce a minimum 1.5s display time using Date.now() comparison:

    JavaScript 
    const splashStart = Date.now();

async function initApp() {
  await loadMemberData();
  await checkDeviceApproval();

  // Ensure splash shows for at least 1.5 seconds
  const elapsed = Date.now() - splashStart;
  const remaining = Math.max(0, 1500 - elapsed);
  await new Promise(resolve => setTimeout(resolve, remaining));

  hideSplash();
  showMainApp();
}

    Key Concepts Explained

    REST API vs FlockTrack

    REST uses different HTTP methods (GET/POST/PUT/DELETE) for different operations. FlockTrack is "REST-ish": all GET, action specified in JSON body. It's a pragmatic RPC-over-HTTP pattern, not strict REST.

    IndexedDB vs localStorage

    localStorage: synchronous, 5MB, strings only. IndexedDB: async, hundreds of MB, stores objects with indexes. For an offline queue of structured records, IndexedDB is the only viable option.

    Cache API

    A browser API that stores HTTP request/response pairs. The Service Worker uses it to serve cached responses when offline. It's separate from the browser's default HTTP cache and fully programmable.

    Web App Manifest

    A JSON file (manifest.json) that tells the browser this site can be installed as an app. Defines the app name, icons, theme, and how it should launch (standalone vs in browser).

    Event-Driven Architecture

    The app doesn't poll continuously. It reacts: user taps (event), network comes back (event), sync timer fires (event), visibility changes (event). Each event triggers a specific handler.

    PWA vs Native App

    PWA: no app store, instant updates, cross-platform, limited hardware access. Native: app store distribution, full hardware APIs, larger install size. For attendance tracking, PWA is sufficient and eliminates the app store friction.

    "Google Sheets is a real database." No. It's a spreadsheet being used as a database. It has no ACID guarantees, no transactions, no query optimizer, no connection pooling. It works for FlockTrack because the access pattern is simple (append-only writes, full-table reads) and the scale is small (hundreds of rows, not millions). At 10x scale, you'd migrate to Firebase or Supabase.

    "GET requests can't send data." They can. Query parameters ARE data. The limitation is URL length (~2048 chars) and the convention that GET should be idempotent. FlockTrack violates the convention intentionally because of the iOS Safari bug, and the payloads are small enough to fit in URLs.

    Fire-and-Forget Pattern

    This is the core UX philosophy of FlockTrack. The user should NEVER wait for the network. Every action completes locally in under 50ms, and the network call happens silently in the background.

    Fire-and-forget means: The UI responds to the user action IMMEDIATELY based on local state. The network request fires asynchronously. If it succeeds, great. If it fails, the app queues it for retry. The user never sees a loading spinner for check-ins.

    JavaScript 
    async function checkIn(memberId) {
  // IMMEDIATE: Update local state and UI
  const member = getMemberFromCache(memberId);
  addToLocalAttendance(member);
  renderAttendanceList();
  showToast(`${member.name} checked in!`);
  if (navigator.vibrate) navigator.vibrate(50);

  // BACKGROUND: Network sync (user doesn't wait for this)
  syncToServer({ action: 'checkIn', memberId, timestamp: Date.now() })
    .catch(err => {
      // Silent failure - already in IndexedDB, will retry
      console.log('Sync failed, queued for retry:', err.message);
    });
}

// The user saw "checked in!" 200ms ago.
// The network request might still be in flight.
// Or it might have failed. Doesn't matter - it's queued.

    Q: "How do you make your app feel fast?"

    I use a fire-and-forget pattern. Every user action (check-in, adding a member, visitor registration) writes to IndexedDB first and updates the UI immediately. The server sync happens asynchronously in the background. This means the perceived latency is always under 50ms regardless of network speed. If the network fails, the change is queued and retried later. The user never sees a spinner for core actions.

    Fire-and-forget = Dropping a letter in a mailbox. You drop it in and walk away. You don't stand there waiting for the postal service to deliver it. You trust the system will eventually deliver it. If the mailbox is full, you come back later. The act of "sending" is instant from your perspective.

    Optimistic UI Updates

    The UI shows the result of an action BEFORE the server confirms it. This is called "optimistic updating." You're optimistic that the server will accept it (which it almost always does). On the rare occasion it doesn't (duplicate check-in, expired member), the next sync cycle corrects the local state.

    Optimistic UI

    Show success immediately, reconcile with server later. 99% of the time the server agrees. 1% gets auto-corrected.

    Pessimistic UI

    Wait for server confirmation before showing success. Feels slow. Loading spinners everywhere. Used in banking apps where errors are costly.

    "Optimistic UI means you lose data." No. The data is safely in IndexedDB. "Optimistic" means you show the result before server confirmation, not that you discard the data. The local database IS a real database. The sync queue ensures nothing is lost. The worst case is the UI shows "checked in" and then 30 seconds later silently removes it because the server rejected it (already checked in today).

    Event-Driven Architecture

    FlockTrack doesn't use a polling loop or a framework's reactive state system. It's built on browser-native events and custom events that trigger specific handlers.

    Network Events

    online, offline. Browser tells the app when connectivity changes. Triggers sync flush or pause.

    Visibility Events

    Timer Events

    Service Worker Events

    install, activate, fetch. Lifecycle events that manage the cache and offline capability.

    IndexedDB Events

    onsuccess, onerror, onupgradeneeded. Async database operations complete via callbacks.

    Q: "Explain event-driven architecture."

    Instead of the app constantly checking "did anything change?" (polling), it registers handlers for specific events and reacts only when something happens. In FlockTrack, the browser fires an 'online' event when WiFi reconnects, which triggers my sync function. A 'visibilitychange' event fires when the user returns to the tab, which refreshes data.     Member Registration Flow

    The end-to-end journey from "new member wants to join" to "member can check in with QR code."

    Step-by-Step Flow

    1. Church shares a Google Form link (via QR poster at entrance, Facebook group, etc.)
    2. New member fills the form: name, email, phone, uploads a selfie
    3. Google Form saves response to a connected Sheet
    4. Apps Script onFormSubmit trigger fires automatically
    5. Script checks for duplicate names using namesMatch()
    6. If unique: generates UUID, creates Members row, generates QR image URL
    7. Script emails the member their personal QR code with instructions
    8. Member saves QR to phone. Next Sunday, they show it at the door.
    JavaScript 
    // Google Form trigger (runs server-side in Apps Script)
function onFormSubmit(e) {
  const lock = LockService.getScriptLock();
  lock.waitLock(10000); // Prevent race conditions

  try {
    const name = e.namedValues['Full Name'][0].trim();
    const email = e.namedValues['Email'][0].trim();
    const phone = e.namedValues['Phone'][0] || '';
    const photoUrl = e.namedValues['Photo'][0] || '';

    // Duplicate check
    const members = getMembersSheet().getDataRange().getValues();
    const isDuplicate = members.some(row => namesMatch(row[COL_MEM.NAME - 1], name));

    if (isDuplicate) {
      // Email admin about potential duplicate
      notifyAdmin(`Potential duplicate registration: ${name}`);
      return;
    }

    // Generate unique ID
    const memberId = Utilities.getUuid();

    // Write to sheet
    getMembersSheet().appendRow([
      memberId, name, email, phone, photoUrl, '',
      'General', 'Active', new Date()
    ]);

    // Generate and email QR
    const qrImageUrl = `https://api.qrserver.com/v1/create-qr-code/?size=300x300&data=${memberId}`;
    sendWelcomeEmail(email, name, qrImageUrl);

  } finally {
    lock.releaseLock();
  }
}

    Why LockService? If two people submit the form at the exact same time, two instances of onFormSubmit run in parallel. Without a lock, both might read the members list, both see no duplicate, and both write; creating a duplicate. LockService makes the second execution wait until the first finishes. It's Apps Script's version of a mutex.

    Sync Cycle Deep-Dive

    The sync cycle is the heartbeat of the offline-first system. It runs every 30 seconds (when online) and does two things: pushes local changes to the server, and pulls server truth to local.

    JavaScript 
    async function syncCycle() {
  if (!navigator.onLine) return;
  if (syncInProgress) return; // Prevent overlapping syncs
  syncInProgress = true;

  try {
    // PHASE 1: Push outgoing queue
    const queue = await getAllFromStore('syncQueue');
    let pushed = 0;

    for (const item of queue) {
      if (isBlacklisted(item.memberId)) {
        await deleteFromStore('syncQueue', item.id);
        continue;
      }

      try {
        const result = await apiCall(item.payload);
        if (result.status === 'success' || result.status === 'already_checked_in') {
          await deleteFromStore('syncQueue', item.id);
          pushed++;
        }
      } catch (networkError) {
        break; // Stop pushing, retry next cycle
      }
    }

    // PHASE 2: Pull fresh server state
    const serverAttendance = await apiCall({ action: 'getTodayAttendance' });
    if (serverAttendance && serverAttendance.records) {
      // Detect deletions (records we had locally but server doesn't)
      const localRecords = await getAllFromStore('attendance');
      const serverIds = new Set(serverAttendance.records.map(r => r.memberId));

      for (const local of localRecords) {
        if (!serverIds.has(local.memberId)) {
          blacklistMember(local.memberId); // Prevent re-push
        }
      }

      // Replace local with server truth
      await clearStore('attendance');
      for (const record of serverAttendance.records) {
        await saveToIndexedDB('attendance', record);
      }

      renderAttendanceList(); // Update UI with fresh data
    }

    // Update sync status indicator
    updateSyncBadge(pushed, queue.length);

  } finally {
    syncInProgress = false;
  }
}

    Push then Pull. Always push first, then pull. If you pull first, you'd overwrite local changes that haven't been pushed yet. The queue ensures nothing is lost. After pushing, you pull the authoritative server state and replace local cache entirely. This two-phase approach guarantees eventual consistency without complex merge logic.

    Q: "How do you handle data consistency between client and server?"

    I use a push-then-pull sync cycle. Local writes go to an IndexedDB queue. Every 30 seconds, the app pushes queued items to the server, then pulls the full server state for today. The server is always authoritative; after pulling, local state is completely replaced. This gives eventual consistency without conflict resolution logic. The trade-off is that very recent check-ins (under 30 seconds old) might temporarily show differently on two devices, but they converge at the next sync. For a church attendance use case, 30-second convergence is perfectly acceptable.

    Error Handling Strategy

    In an offline-first app, errors are expected. The network WILL fail. The camera WILL glitch. The server WILL be slow. Every error path must be designed, not just caught.

    Error Categories

    Network Errors

    Handled by sync queue. Check-in saved locally, retried later. User never sees a network error for core flows.

    Server Errors

    Apps Script returns {error: message}. Shown as a toast. Non-blocking. User can continue working offline.

    Camera Errors

    Permission denied, hardware failure, track ended. Graceful fallback to Quick Tap or Search method.

    IndexedDB Errors

    Storage full, permission denied (private browsing). Shown as warning. App still works for single-session use.

    JavaScript 
    // Graceful camera error handling
async function startScanning() {
  try {
    await qrScanner.start(
      { facingMode: "environment" },
      { fps: 10, qrbox: { width: 250, height: 250 } },

      switchToQuickTap();
    }
  }
}

// API call wrapper with timeout
async function apiCall(payload, timeoutMs = 15000) {
  const url = SCRIPT_URL + '?data=' + encodeURIComponent(JSON.stringify(payload));
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeoutMs);

  try {
    const response = await fetch(url, { signal: controller.signal });
    clearTimeout(timer);
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    return await response.json();
  } catch (err) {
    clearTimeout(timer);
    if (err.name === 'AbortError') throw new Error('Request timed out');
    throw err;
  }
}

    Q: "How do you handle errors in a user-facing app?"

    I categorize errors by impact. Network errors are invisible to the user because the offline queue handles them silently. Camera errors trigger a graceful fallback to an alternative check-in method (photo grid or search). Server errors show a non-blocking toast notification. The principle is: never let an error stop the user from completing their task. Always offer an alternative path. Critical errors (IndexedDB failure) get a clear explanation of what happened and what to do (refresh the page, clear browser data).

    Google Apps Script: Quirks and Workarounds

    Cold Starts

    When no one has called your Apps Script in ~5 minutes, the next request takes 2-5 seconds (cold start). Google spins down inactive scripts to save resources. This isn't a bug, it's serverless behavior (same as AWS Lambda cold starts).

    JavaScript 
    // Frontend: handle cold start gracefully
async function apiCallWithRetry(payload) {
  const TIMEOUT_FIRST = 10000;  // 10s for potentially cold start
  const TIMEOUT_RETRY = 5000;   // 5s for warm retry

  try {
    return await apiCall(payload, TIMEOUT_FIRST);
  } catch (err) {
    if (err.message === 'Request timed out') {
      // Cold start might have warmed it up, retry immediately
      return await apiCall(payload, TIMEOUT_RETRY);
    }
    throw err;
  }
}

    The 302 Redirect Issue

    When you deploy Apps Script as "Execute as: Me" and "Access: Anyone," Google adds a 302 redirect from script.google.com to a unique execution URL. This redirect is where iOS Safari drops POST bodies. Other browsers handle it fine. This is documented in Google's issue tracker but never fixed.

    Request flow (what actually happens):

    text 
    1. Client sends GET to: https://script.google.com/macros/s/ABC123/exec?data={...}
2. Google responds: 302 Redirect -> https://script.googleusercontent.com/macros/echo?...
3. Browser follows redirect (GET params preserved in URL)
4. Apps Script doGet(e) receives the request with e.parameter.data intact

If this were POST:
1. Client sends POST to: https://script.google.com/macros/s/ABC123/exec
   Body: data={...}
2. Google responds: 302 Redirect
3. iOS Safari follows redirect but DROPS the POST body
4. Apps Script doGet(e) receives empty request -> fails silently

    Interview Prep Answers

    Q: "What's the most challenging bug you've solved?"

    The ghost sync bug. After an admin deleted a check-in from the server, the device that originally recorded it would re-push the check-in on its next sync cycle, effectively undoing the deletion. The root cause was that the device's IndexedDB still had the record and the sync logic assumed local data was always valid to push. My fix was a 60-second blacklist: when a sync reveals a record was deleted server-side, that member ID is blacklisted locally for 60 seconds, preventing re-push. By the next sync cycle, the local store has been refreshed from the server and the deleted record is gone.

    Q: "How would you scale this?"

    Google Sheets hits limits around 10K rows and concurrent writes. The migration path is clear: (1) Replace Google Sheets with Firebase Firestore (still free tier viable, real-time sync, proper queries). (2) Replace Apps Script with Firebase Cloud Functions (same JavaScript, proper HTTP handling). (3) Keep the PWA frontend as-is; only the API URL changes. The offline-first architecture with IndexedDB remains identical. The abstraction between frontend and backend (JSON over HTTP) makes this swap straightforward.

    Q: "What would you do differently?"

    Three things. First, I'd add TypeScript from the start; even in a single file, type annotations prevent bugs as complexity grows. Second, I'd implement versioned sync; right now the full attendance list refreshes each cycle, but a diff-based sync (only send changes since last sync timestamp) would reduce bandwidth. Third, I'd add error boundaries; currently, a failed API call during sync silently retries, but there's no user-visible indication of sync staleness beyond manual checking.

    Q: "Why not use Firebase from the start?"

    Constraint-driven design. The church needed zero recurring costs and zero vendor lock-in beyond Google. Google Sheets is something any church admin can open and understand; it's literally a spreadsheet. Firebase would be more powerful but requires a Google Cloud billing account (even on free tier), and the data lives in a proprietary database only developers can access. With Sheets, the pastor can open it and see today's attendance. That accessibility was a hard requirement.

    Q: "How do you test this?"

    Manual testing with multiple devices (Android, iPhone, desktop). For offline scenarios, I use Chrome DevTools to simulate offline mode and verify IndexedDB writes. For the Apps Script backend, I use the built-in execution log and test with curl commands. I don't have automated tests; for a side project of this scope, the cost of setting up a test framework exceeds the bug-prevention benefit. If this were a team project or growing in complexity, I'd add Jest for the frontend logic and clasp for Apps Script unit tests.

    Q: "Explain your app's data flow in 30 seconds."

    User taps check-in. The app writes to IndexedDB immediately, so the UI confirms instantly. In the background, it sends an HTTPS GET request to Google Apps Script with the member ID encoded as JSON in the URL. Apps Script parses it, appends a row to the Attendance sheet, and returns success. If the network is down, the check-in stays in a local sync queue and retries every 30 seconds. When connection returns, the queue flushes and local data refreshes from the server.

    Q: "What design patterns did you use?"

    Several. Observer pattern: event listeners for network status, visibility changes, and user actions. Queue pattern: IndexedDB sync queue for reliable message delivery. Cache-aside pattern: Service Worker checks cache first, falls back to network. Optimistic concurrency: UI updates immediately, reconciles with server truth later. Facade pattern: the apiCall() function hides the complexity of JSON encoding, URL construction, timeout management, and error handling behind a simple interface.

    Q: "How does the QR code system work?"

    Each member gets a unique UUID when they register via Google Form. That UUID is encoded into a QR code image and emailed to them. At church, the greeter opens FlockTrack's scan mode, which activates the device camera using the html5-qrcode library. When the camera reads a QR, it decodes the UUID, looks it up in the local member cache, and fires a check-in. The whole scan-to-confirmed flow takes under 500ms because the member lookup is local (IndexedDB cache) and the check-in is fire-and-forget.

    Q: "What's the difference between a PWA and a native app?"

    A PWA runs in the browser engine, is installed from a URL (no app store), updates automatically on next load, and works cross-platform with one codebase. A native app is compiled for a specific OS, distributed through app stores, requires manual updates, but gets full hardware API access (Bluetooth, NFC, file system). For FlockTrack, a PWA is ideal because we only need camera access (Web API supports it), the church doesn't want to manage App Store/Play Store listings, and instant updates mean bug fixes deploy immediately without waiting for store review.

    Q: "Walk me through what happens when the user has no internet."

    First, the app loads because the Service Worker serves index.html from cache. The member list loads from IndexedDB (cached from last sync). The user taps a member to check in. The check-in writes to IndexedDB's attendance store AND adds an entry to the sync queue. The UI shows "Checked in!" with a small "pending sync" indicator. Every 30 seconds, the sync cycle checks navigator.onLine. When the browser detects connectivity (WiFi reconnects), the 'online' event fires, triggering an immediate sync. The queue flushes all pending check-ins to the server. Then the app pulls fresh data from the server and updates the UI. The user may not even notice it was offline.

    Q: "What happens if two people check in the same member simultaneously from different devices?"

    Both devices save locally and both push to the server. The server's check-in handler queries the Attendance sheet for today's date + that member ID. The first push succeeds and writes a row. The second push finds the existing row and returns {status: 'already_checked_in'}. Both devices show success locally (optimistic UI). On the next sync pull, both devices get the same single attendance record from the server. No duplicate row in the sheet. The deduplication happens server-side via the "check before write" pattern.

    Quick Reference: Technical Vocabulary

    PWA

    Progressive Web App. Web site that passes installability criteria (HTTPS + manifest + Service Worker).

    Service Worker

    Background script that intercepts fetch requests. Enables offline caching and push notifications.

    IndexedDB

    Browser-native NoSQL database. Async, transactional, stores structured data up to hundreds of MB.

    Cache API

    Stores HTTP Response objects keyed by Request. Used by Service Worker for offline asset serving.

    Web App Manifest

    JSON file that declares app metadata (name, icons, display mode) for installability.

    Optimistic UI

    Show action result before server confirms. Revert if server rejects. Feels instant.

    Fire-and-Forget

    Execute async operation without awaiting result. Handle success/failure in background callback.

    Eventual Consistency

    All nodes converge to same state given enough time. Not instantly consistent, but guaranteed eventually.

    Cold Start

    First invocation of a serverless function after idle period. Incurs initialization overhead (2-5s).

    Mutex / Lock

    Mechanism to prevent concurrent access. Apps Script's LockService prevents duplicate registrations.

    Debouncing

    Delay execution until input stops. Prevents firing on every keystroke in search.

    Idempotent

    Same request can be sent multiple times with same result. FlockTrack's check-in is idempotent (server deduplicates).

    Architecture Decision Records

    ADR-001: Why Google Sheets over Firebase?

    ▼

    Context: Need a free, accessible backend for church attendance.

    Decision: Google Sheets as database, Apps Script as API.

    Reasons: (1) Zero cost, no billing account needed. (2) Church admins can open Sheets directly and see/edit data. (3) Built-in formulas for quick reports. (4) No vendor lock-in beyond Google ecosystem they already use.

    Trade-offs: No real queries, slow at scale, no ACID. Acceptable for 500 members and append-only writes.

    Revisit when: Members exceed 2000 or concurrent users exceed 10.

    ADR-002: Why Vanilla JS over React?

    ▼

    Context: Need fast, offline-capable, easily cacheable frontend.

    Decision: Single HTML file with inline CSS and JS, no framework.

    Reasons: (1) One file = one cache entry = trivial Service Worker. (2) No build step = edit and deploy in seconds. (3) No framework bundle = faster first paint. (4) Total control over DOM = easier to debug camera/offline edge cases.

    Trade-offs: Manual DOM manipulation, no component reuse, harder to scale codebase past 3000 lines.

    Revisit when: App grows beyond 3 views or needs complex state management.

    ADR-003: Why Offline-First over Online-First?

    ▼

    Context: Church venue has unreliable WiFi. Sunday morning = 500 people on same network.

    Decision: All check-ins write locally first, sync to server in background.

    Reasons: (1) Check-in must work even with zero connectivity. (2) User experience must be instant (no spinners). (3) Multiple devices can operate independently and converge later.

    Trade-offs: Eventual consistency (not instant). Deleted records can ghost-sync back (solved with blacklist). More complex sync logic.

    Revisit when: Real-time features needed (live attendance count for projector display).

    ADR-004: Why GET for Writes?

    ▼

    Context: iOS Safari drops POST body on Apps Script's 302 redirect.

    Decision: All API calls use GET with JSON-encoded query parameter.

    Reasons: (1) Works on ALL browsers/devices without exception. (2) Simple to implement and debug (URL visible in DevTools). (3) Payloads are small (member ID + timestamp fits easily in URL).

    Trade-offs: Violates REST semantics. URL length limited to ~2048 chars. Server logs expose payload data. Acceptable for internal church app.

    Revisit when: Payloads exceed 1KB or security audit requires POST-only writes.

    Service Worker Versioning

    When you update the app, you bump the CACHE_NAME version string in sw.js. Next time a user opens the app, the browser detects the SW file changed, installs the new version, and on the NEXT page load activates it (replacing old cache with new assets).

// After update (just bump the version):
const CACHE_NAME = 'flocktrack-v3';

// The activate event handler automatically deletes old caches:
self.addEventListener('activate', event => {
  event.waitUntil(
    caches.keys().then(keys =>
      Promise.all(
        keys.filter(k => k !== CACHE_NAME)  // Delete anything that's not v3
            .map(k => caches.delete(k))
      )
    )
  );
});

    Q: "How do you deploy updates to users?"

    I push to GitHub's main branch, and GitHub Pages serves the new version within 60 seconds. When users open the app, the browser checks if sw.js has changed. If the CACHE_NAME version string is different, it installs the new Service Worker, which re-caches all assets. On the next page load, the new version activates and the old cache is deleted. Users always get the latest version without manual intervention, no app store review, no forced updates. It's one of the key advantages of PWA over native apps.

    Security Model

    FlockTrack is an internal church tool, not a banking app. The threat model is "prevent casual unauthorized access," not "defend against skilled attackers." The security is proportional to the risk.

    Layers of Protection

    Device Fingerprint

    Each device has a UUID in localStorage. Must be admin-approved. Prevents random people from checking in members.

    Apps Script Auth

    Script executes as the owner's Google account. Sheet access is controlled by Google's sharing permissions. Only the script can write.

    HTTPS Only

    GitHub Pages enforces HTTPS. All data in transit is encrypted. No one can sniff check-in traffic.

    No Sensitive Data

    The app stores names, emails, and attendance dates. No passwords, no financial data, no health records. Low-stakes data reduces security requirements.

    What's NOT Secured (and why that's OK)

    "The API URL is public, anyone can call it." True. But every request requires a valid device fingerprint that's been admin-approved. Unapproved devices get rejected. Could someone reverse-engineer a valid fingerprint? Theoretically yes, but the reward (marking someone present at church) doesn't justify the effort. Security is always proportional to the value of what you're protecting.

    Technical Decisions You Made (and Why)

    • Vanilla JS over React: Zero build step, single cache entry, full control over camera/offline edge cases
    • GET over POST: iOS Safari drops POST body on Apps Script's 302 redirect
    • IndexedDB over localStorage: Structured data, async, larger capacity, proper transactions
    • Cache-first over network-first: App must load instantly even offline; stale assets are acceptable
    • Server-authoritative over client-authoritative: Prevents conflicts; simple deduplication
    • Device fingerprint over user login: Shared devices at church door; no one wants to log in to mark attendance
    • Single file over module splitting: Simpler caching, faster load, acceptable at 2000 lines
    • Google Sheets over Firebase: Non-technical admins can read/edit data directly; truly zero cost

    Bugs That Show Engineering Maturity

    These are the stories interviewers remember. Each one shows debugging skill and real-world thinking:

    • Ghost sync: Deleted records reappearing because device re-pushed from local cache. Fixed with 60s blacklist.
    • iOS camera leak: Camera staying active after tab switch causing overheating. Fixed with explicit track stopping on visibilitychange.
    • POST body vanishing: Silent failure on iPhones only. Root caused to Safari + 302 redirect interaction. Fixed by switching to GET.
    • Flip camera black screen: Must await scanner.stop() before restarting with new facing mode. Race condition.
    • Splash screen flicker: Sub-100ms load caused jarring flash. Fixed with Date.now() minimum delay of 1.5s.
    • Duplicate names: "Maria Santos" vs "Maria C. Santos". Fixed with fuzzy namesMatch() normalization.
