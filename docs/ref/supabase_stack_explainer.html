From FlockTrack to Supabase Stack

A mental model for tracking what's happening at every layer

1 The Big Picture: Same Sandwich, Different Bread

Every web app is just 3 layers. You already know them. The tools just changed.

🟡 FlockTrack (What You Know)

  • Frontend: HTML/CSS/JS files served by Apps Script
  • Backend: Google Apps Script (.gs files)
  • Database: Google Sheets (rows = records)
  • Auth: Google account (automatic)
  • Hosting: Google deploys it for you

🟢 Church Inventory (Supabase Stack)

  • Frontend: React components (Next.js pages)
  • Backend: Next.js API routes + Supabase client calls
  • Database: PostgreSQL (real SQL tables in Supabase)
  • Auth: Supabase Auth (email/password, managed for you)
  • Hosting: Vercel (auto-deploys from GitHub)
💡 Key insight: In FlockTrack, Google handled everything invisibly. In the Supabase stack, each layer is a separate service you can see and control. More power, but more pieces to track.

4 How Data Flows (Side by Side)

Example: User adds a new inventory item

🟡 FlockTrack Way

  • User fills HTML form
  • JS calls google.script.run.addItem(data)
  • addItem() in Code.gs runs
  • It does sheet.appendRow([name, qty, ...])
  • Row added to Sheet
  • Callback updates the HTML

🟢 Supabase Way

  • User fills React form component
  • Component calls supabase.from('inventory_items').insert({...})
  • Supabase receives the request
  • PostgreSQL inserts the row
  • Response comes back with the new row
  • React re-renders the list
FlockTrack:
  [HTML Form] → google.script.run → [Code.gs] → Sheet.appendRow() → [Google Sheet]

Supabase Stack:
  [React Form] → supabase.from().insert() → [Supabase API] → PostgreSQL INSERT → [Database]

Reading data:
  FlockTrack:  sheet.getRange().getValues() → returns 2D array [[row1], [row2]]
  Supabase:    supabase.from('table').select() → returns array of objects [{id, name, ...}]

5 New Concepts You Need (That FlockTrack Hid From You)

🔑 Authentication & Sessions

FlockTrack: Google handled it. User was already logged into Google.

Supabase: YOU manage auth. Supabase gives you functions like supabase.auth.signUp(), signInWithPassword(), getUser(). A session token (JWT) is stored in cookies. The middleware.ts file checks this token on every page load to decide if user is logged in.

Your file: src/middleware.ts = the bouncer at the door. src/lib/supabase/server.ts = how the server knows who's asking.

🗃️ Migrations (Database Schema Versioning)

FlockTrack: You just added a column to the Sheet manually.

Supabase: You write a .sql file that says "CREATE TABLE..." and it runs once. If you need to change the schema later, you write another migration file. This keeps a history of all database changes (like git for your DB structure).

Your file: supabase/migrations/001_initial_schema.sql = this created ALL your tables, enums, and relationships.

📡 Client vs Server (Two Ways to Talk to DB)

FlockTrack: Everything went through Code.gs (server only).

Supabase: You have TWO connection modes:

  • client.ts (browser-side): Used in React components. Limited by Row Level Security (RLS) policies. User can only see/edit what policies allow.
  • server.ts (server-side): Used in API routes and server components. Has the user's session from cookies. Can do privileged operations.

Think of it as: client.ts = the user doing things directly. server.ts = your Code.gs doing things on behalf of the user.

🛡️ Row Level Security (RLS)

FlockTrack: Anyone with the Sheet link could see everything. You filtered in code.

Supabase: The DATABASE itself enforces who can see what. You write policies like "users can only SELECT rows where ministry_id matches their own ministry." Even if someone hacks the frontend, the DB won't give them other people's data.

This is like putting a lock on each Sheet tab that only opens for specific people, enforced by Google itself (not your code).

⚡ React Query (Data Fetching Layer)

FlockTrack: You called google.script.run, waited, then manually updated the HTML.

React Query (@tanstack/react-query) automates: loading states, caching, refetching, error handling. You define a query once, and it handles "show spinner while loading", "cache for 5 min", "refetch when tab is focused".

It's like having a smart assistant between your UI and your data calls that handles all the boring stuff.

🧩 Components (Reusable UI Pieces)

FlockTrack: You copy-pasted HTML blocks or used template literals in JS.

React: Each UI piece is a function that returns HTML-like code (JSX). A Button, a Table, a Modal are all components. You import and reuse them. Props = parameters you pass in.

<InventoryTable items={data} /> is like calling renderTable(data) in your old code, but it auto-updates when data changes.

6 Development Stages (So You Can Track Progress)

Here's how to think about building in stages, same way you tracked FlockTrack:

Stage 1: Database Design

Write migration SQL. Define tables, relationships, enums. This is your foundation.

FlockTrack equiv: Creating all your Sheet tabs and column headers

Stage 2: Auth Setup

Login/register pages, middleware, protected routes. Users can sign up and get sessions.

FlockTrack equiv: Was free (Google login). Now you build it.

Stage 3: Core CRUD Pages

Build pages that Create, Read, Update, Delete data. One feature at a time (inventory first, then requests, etc).

FlockTrack equiv: Building each HTML page + its Code.gs functions

Stage 4: Business Logic

Workflows (request approval flow, stock movement tracking, notifications). The "smart" part.

FlockTrack equiv: Your complex .gs functions that moved data between sheets

Stage 5: Polish & Deploy

Error handling, loading states, mobile responsive, deploy to Vercel.

FlockTrack equiv: Making it look nice + deploying as web app
